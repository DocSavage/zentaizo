# Integrating `zen-segmend-mesher` workspace conventions back into the templates

_Round 1. Integrated 2026-05-17 (commit `f31cfe9`). Covers workspace commits through `410eef7` (2026-05-16). Round 2 is recorded in [`zen-segmend-mesher-template-integration-round-2.md`](zen-segmend-mesher-template-integration-round-2.md)._

## Context

`zen-segmend-mesher` was the first Zentaizo workspace driven hard against real multi-week, multi-agent, multi-branch implementation work. Across ~60 commits the workspace's own `AGENTS.md` and `skills/plan-and-implement.md` diverged from what `zentaizo create` emits. The workspace's `skills/curate-atlas.md` stayed identical to upstream.

This document records what was changed in the workspace, which of those changes were promoted into the Zentaizo templates here, the architecture decision underlying *where* workspace conventions should live, and the retirement of `zentaizo update` in favour of an AI-driven upgrade procedure.

## Architecture decision: where workspace conventions live

Zentaizo exposes two surfaces that could in principle carry workspace conventions:

1. **Global skill** — `~/.claude/skills/zentaizo/SKILL.md` plus sibling procedure files, installed via `zentaizo skills install`. One per user, typically symlinked to this repo's `templates/global-skills/zentaizo/`.
2. **Workspace files** — `AGENTS.md` generated by `zentaizo create` from `workspace_agents()`, plus `skills/curate-atlas.md`, `skills/plan-and-implement.md`, `skills/plan-template.md` copied from the templates directory.

The decision is to keep workspace conventions (filenames, frontmatter, commit hygiene, branch handling) in the *workspace* files — **not** in the global skill. The global skill stays narrow: what Zentaizo is, what the atlas is for, memory-system boundaries, *where to look*, and now also the experimental upgrade procedure (which is a Zentaizo-meta operation rather than a workspace convention).

Reasons:

- `AGENTS.md` is the file every AI harness reads when in a workspace, regardless of whether the global skill is installed on that machine. Conventions there work for any collaborator.
- `AGENTS.md` is version-pinned to the workspace via the file in git. A workspace keeps the conventions it was last refreshed under. Convention versions belong to the workspace, not to the user's `$PATH`.
- The global skill is per-user; conventions could legitimately differ between workspaces. Putting them in the global skill removes that flexibility.

The global `SKILL.md` already said "Read `AGENTS.md` … before making recommendations." It now also explicitly says the workspace `AGENTS.md` is authoritative for workspace conventions and wins on conflict.

## Retirement of `zentaizo update`; introduction of `upgrade-zentaizo` (experimental)

The previous `zentaizo update` command did a whole-file overwrite of the workspace's Zentaizo-owned files when they differed from the bundled templates. That shape is fundamentally mismatched with how convention drift actually plays out:

- It cannot preserve workspace-local customizations of `AGENTS.md`. A workspace's deliberate project-specific section dies on update.
- It cannot migrate downstream artifacts. When a convention changes — filename pattern, frontmatter field name, directory layout — the session files already on disk need rewriting and renaming. The CLI cannot safely do that. (The `410eef7` migration in `zen-segmend-mesher` is the case in point: 27 files renamed, every cross-reference fixed, frontmatter added.)
- It cannot decide *what* should change. Some template drift is "Zentaizo's conventions evolved — adopt them"; other drift is "this workspace deliberately diverged because its workflow is different." A blind overwrite cannot distinguish those.

`zentaizo update` is therefore **removed**. The replacement is an experimental procedure `skills/upgrade-zentaizo.md` bundled with the global Zentaizo skill (`templates/global-skills/zentaizo/upgrade-zentaizo.md`), referenced from `SKILL.md`. It walks an AI session through:

1. Diffing the installed templates against the workspace's bundled files.
2. Classifying every delta as *template-ahead*, *workspace-ahead*, *both diverged*, or *convention rename*.
3. Planning any artifact migrations that cascade from a convention rename (file renames via `git mv`, frontmatter rewrites, cross-reference updates).
4. Executing on the user's approval as a normal `sessions/changes/` plan, with `git diff` review at each step.

The skill is deliberately experimental: it is bundled in the user's global skill install (opt-in via `zentaizo skills install`), it is **not** auto-installed into every new workspace's `skills/` directory, and the procedure's prose says so up-front. The design will sharpen as the skill is exercised against real workspaces — starting with `zen-segmend-mesher` itself, whose session frontmatter still uses the old `prototype_base_commit:` and `artifact_root:` field names and would benefit from a real run-through.

## What was deliberately NOT promoted

- **`main-0009-zentaizo-workspace-improvements.md`** (in `zen-segmend-mesher/sessions/changes/`) is a meta-plan for Zentaizo itself covering summaries/handoffs, summary frontmatter, stale-summary detection, greenfield/private repo handling, incremental `zentaizo fetch`, and docs snapshot tooling. Its status is `planned`; no implementation followed in either repo. That plan is essentially a Zentaizo backlog already framed in this repo's voice. It is left for a follow-up.
- The `phase1a → phase1z` slug-suffix convention from `a8893ec` was deliberately superseded by `410eef7` (per-branch sequential numbers) and is not preserved.

## Recommended next step for `zen-segmend-mesher`

Now that `zentaizo update` is gone, the right way to bring `zen-segmend-mesher` onto the new templates is an AI session in the workspace itself, driven by `upgrade-zentaizo.md`. Specifically, that session would:

- Adopt the upstream `AGENTS.md` (the six promoted changes plus the generalization renames), preserving anything project-specific the workspace genuinely needs.
- Rewrite session frontmatter: `prototype_base_commit:` → `implementation_base:`, `artifact_root:` → `implementation_outdir:`, and add `branch_prefix:` to any plan that lacks it.
- Fix the leftover stale `YYYY-MM-DD-<slug>` reference in the workspace's "From Brainstorming to Plan" section that the `410eef7` migration missed.

This is also the first real exercise of `upgrade-zentaizo.md`. Expect to refine the skill's procedure based on what shows up in practice.
