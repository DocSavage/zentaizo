# Plan: Rename Zentaizo Config and Add a Model-Agnostic Curation Skill

## Context

Zentaizo (`/Users/katzw/GitHub/zentaizo`, version 0.1.0) is a Python CLI that creates a "workspace" — a directory of pinned repos, docs, papers, and notes that an AI assistant uses to understand a multi-repo system. It's the successor to the user's earlier `~/GitHub/codebase-assistant` work, which was successfully adapted into `~/GitHub/CAVE-docs`.

The user wants two improvements before this design solidifies:

1. **Rename `zentaizo.config.json`** to something more evocative. The file is the human-curated description of "what knowledge belongs to this system" — the heart of the workflow — and the current name underplays that.
2. **Add a procedural skill file** that walks the user (with an LLM facilitator) through populating that file: identifying central repos, supporting repos, public docs, papers, and internal notes. Critical constraint: the skill must be **model-agnostic** (usable by Claude Code, Codex, Gemini, Aider, etc.) and must not conflict with the host tool's memory/rules system (CLAUDE.md, GEMINI.md, etc.).

## Decisions (confirmed with user)

## `skills/curate-atlas.md` outline (~250–300 lines)

Pure markdown, no frontmatter. Structure:

```
# Curate the Zentaizo Atlas

(2-paragraph intro: what zentaizo.atlas.json is, why a curated source list
matters for multi-repo work, how this file fits into the workflow.)

## When to run this procedure

- The atlas is empty (the user just ran `zentaizo create`).
- The user explicitly asks to "set up", "fill out", "populate", "add to" the atlas.
- A new repo / doc / paper has appeared in the system and should be tracked.
- The user is editing zentaizo.atlas.json and asks for help.

## Boundaries — what this procedure does NOT do

This procedure curates a list of *sources* (repos, docs, papers, notes) that
belong to one system. It does NOT record:

- User preferences, coding style, or personal context (those belong in the
  host LLM's memory/rules file: CLAUDE.md / MEMORY.md for Claude Code,
  GEMINI.md for Gemini, .codex/AGENTS.md for Codex, .aider.conf.yml for
  Aider, and so on).
- Project-wide conventions or build commands (those belong in AGENTS.md
  at the workspace root or in the source repos themselves).
- Generated summaries (those belong in summaries/, produced by
  `zentaizo summarize`).

If the user mentions a fact that belongs in one of those other files,
say so and let them decide where it lives — do not silently merge it
into the atlas.

## Pre-flight check

1. Confirm zentaizo.atlas.json exists at the workspace root. If not, ask
   the user to run `zentaizo create` first.
2. Read the current atlas in full before asking any questions. The user
   may already have entries; the goal is to extend or refine, not
   re-interview from scratch.
3. Read AGENTS.md for any system-specific guidance.

## The interview

Ask one question at a time. Wait for an answer. Do not pre-fill answers
the user did not give.

### Step 1 — What system is this atlas about?
   - Confirm `name` (defaults to workspace dir name).
   - Confirm or write a 1-3 sentence `description`.

### Step 2 — Central repos (typically 1-3)
   - "What is the primary code that makes this system run or are we starting a greenfield project?"
   - For each: name, URL, ref strategy, 1-line description.

### Step 3 — Supporting repos
   - Client libraries, web frontends, deployment configs, scheduled jobs,
     dev tooling. "What other code does the system depend on or interact
     with?"

### Step 4 — Public documentation
   - API references, vendor docs, public wikis. URLs only; snapshot
     download is a future zentaizo command.

### Step 5 — Papers and design docs
   - Specs, RFCs, academic papers, internal design docs. Skip if none.

### Step 6 — Internal notes
   - Issue threads, postmortems, oncall traces, scratch findings the
     user wants the assistant to consult. Skip if none.

### Step 7 — Picking ref values

A short decision tree:
   - Day-to-day exploration: use `main` (or the repo's default branch).
   - Reproducible context for a specific question: pin to a commit SHA.
   - Stable contract while a system evolves: pin to a tag.

### Step 8 — Description quality

Each entry's `description` should answer "why does this belong in the
atlas?" Good: "REST API for creating and resolving short links". Bad:
"the API repo".

## Writing the atlas

1. Show the user a unified diff of proposed atlas changes before saving.
2. Preserve any existing entries the user did not modify.
3. Write the file as JSON with 2-space indent and a trailing newline.
4. Suggest the user commit the change with a meaningful message.

## Validate and lock

   - Run `zentaizo validate` and resolve any errors before fetching.
   - Run `zentaizo fetch` to clone/update repos and write
     zentaizo.lock.json with resolved commit SHAs.
   - For first-time setup, follow with `zentaizo summarize` and ask the
     LLM to populate `summaries/` from the prompt template.

## Re-invocation

If this procedure is run a second time on a workspace whose atlas is
already populated, do not start over. Open with: "Your atlas already
has N repos, M docs, P papers, Q notes. What would you like to change?"
```

The skill is reference-only: it doesn't import or depend on any host-tool-specific feature. Auto-discovery happens because `AGENTS.md` (which every model-agnostic coding assistant reads) points at it.

## AGENTS.md additions (in `workspace_agents()` template, `cli.py:127`)

Append a new section after the existing "Source Consultation":

```
## Curating the Atlas

The system's source list lives in `zentaizo.atlas.json`. To populate or
extend it, follow the procedure in `skills/curate-atlas.md` — interview
the user, propose a diff, validate, then run `zentaizo fetch`.

Do not put user-specific facts (preferences, environment, coding style)
into the atlas. Those belong in the host tool's memory or rules file
(e.g. CLAUDE.md, GEMINI.md, .codex/, .aider.conf.yml). The atlas is
data about the *system*; the host file is data about the *user*.
```

This makes the boundary explicit and travels with every workspace.

## Pitfalls to avoid

1. **Package-data omission** — without the `pyproject.toml` entry, the wheel won't ship the markdown. Verify with both editable install (`pip install -e .`) and wheel build (`python -m build && pip install dist/*.whl` in a clean venv).
2. **`importlib.resources` API** — use `importlib.resources.files("zentaizo") / "templates" / "skills"` (Python 3.9+; the project requires 3.11+ per `pyproject.toml:10`). Don't use deprecated `pkg_resources`.
3. **`shutil.copytree` collision** — destination must not pre-exist. Pass `dirs_exist_ok=True` only if you want idempotent reinstalls (probably yes, since `create` already errors on non-empty target before reaching this point).
4. **Don't introduce `.claude/` or other tool-specific directories** — that's the explicit constraint. The only directories `zentaizo create` writes are model-agnostic ones.
5. **Don't include YAML frontmatter in `curate-atlas.md`** — even harmless frontmatter biases readers toward thinking it's tool-specific.
6. **`workspace_readme` consultation order** — its current step list (`summaries/`, `repos/`, `docs/`, `papers/`, `notes/`) is *for using* the workspace. Keep that intact; add a separate "Setup" pointer to `skills/curate-atlas.md` so the two lifecycles (set up the atlas vs. answer questions from it) don't blur.
7. **Test that `provide-info` is unaffected** — the reference block injected into a target repo's `AGENTS.md` should be unchanged. The atlas filename never appears there (only `LOCK_NAME` and `summaries/`/`repos/` paths), so this is a regression-only check.
